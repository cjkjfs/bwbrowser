
## 视频下载 Cookie 来源链路诊断 + 代理跟随修复（2026-11-19）

### 诊断结论（用户问「下载为什么失败/提取哪个账号/链路不通吗」）
- **链路是通的**：真日志在 `video-tools/logs/download_<task>.log`（BwBrowser.log 是 0 字节，发布版 log::info 被 Off 吞掉；bwbrowser_debug.log 只有网络报文）。
- Cookie 实际提取自**账号 3926**（profile「qq721040_3926」，候选清单第 1 个，实时导出成功，cookies_youtube.txt 8143B 含 SID/SAPISID/__Secure-1PSID 登录会话）。
- 失败真因 = YouTube "Sign in to confirm you're not a bot"：**代理跟随的是手动指定 cookie_account_id=3873，其节点不可用 → 直连**；3926 的 cookie 会话 IP 与直连出口 IP 不匹配触发风控。
- 设置文件：`%LOCALAPPDATA%/BwBrowser/video_download_settings.json`（cookie_account_id=3873）、`settings/cookie_source_accounts.json`（24 账号清单）。

### 修复：代理跟随与 Cookie 提供账号脱节（video_downloader.rs，待重编译）
- `export_vps_cookies_to_file` 返回值改 `Result<(PathBuf, Option<i64>), String>`（携带实际提供 Cookie 的账号 id；VPS 老链路=None），6 个返回点全改。
- `effective_proxy_url(settings, cookie_provider)`：跟随模式优先用实际提供账号（>0），回退 settings.cookie_account_id。
- 主下载流程 + AI 改写音频 + AI 改写字幕 3 处均改为「先提 Cookie → 再按提供账号解析代理」；任务日志新增「代理（跟随实际 Cookie 源账号）: url」行。
- 效果：本次案例中下次下载将跟随 3926 的后台登录节点（IP 与 cookie 同源），3873 节点坏了也不再导致直连。

### 追加：「当前浏览器优先」Cookie 提取（用户需求：正在用的浏览器窗口优先）
- 位置：export_vps_cookies_to_file 内，候选账号链**之前**新增最高优先级。
- 逻辑：遍历 list_profiles，`profile::trash::is_running_locally`（process_id 存活）筛运行中窗口 → `cookie_sync::export_cookies_via_cdp` 从内存实时导出 → 平台校验（youtube 还须 psid/sapisid 登录会话，游客 cookie 会触发人机验证）→ 通过则写 cookie_path 返回。
- profile 名 `_账号id` 结尾时解析 aid（与候选匹配同一约定）供代理跟随同账号节点。
- 校验不过（窗口没登录目标平台）→ log_task 说明 → 落回候选账号链；无运行窗口时行为完全不变。用户场景：sqyacmyxgs@gmail.com 窗口看视频→嗅探下载→直接用该窗口 cookie。

### 追加：多浏览器并发——前台窗口优先（用户问「启动多个浏览器冲突吗」）
- 结论：不冲突（CDP 各连各的调试端口；cookie 按平台分文件、任务先写后读）。多窗口时原实现按 profile 列表顺序取第一个校验通过的，不一定是用户点击的窗口。
- 升级：新增 `foreground_window_pid()`（windows crate GetForegroundWindow+GetWindowThreadProcessId，Win32_UI_WindowsAndMessaging feature 已有）；运行窗口排序把前台窗口排最前（pid 匹配 profile.process_id 或 ChromiumManager find_by_profile），拿不到前台退化为列表顺序。
- 注意事项：并发任务共用 cookies_<平台>.txt 有理论竞态（互相覆盖但都是有效登录 cookie）；非 Windows 平台前台策略自动退化。扩展 enqueue 不带身份（所有 profile 同一端口 10118-10120，body 只有 url），无法从请求侧识别来源窗口，用前台 pid 是最简可靠方案。
