## 「把公司切换放进 company_config.php 能否全站生效」可行性（只读分析）

- 覆盖率（tk/ 顶层 192 个 PHP，排除 .bak）：require `company_config.php` **94**、require `config.php` **169**、调用 `render_header()` **41**（含库自身，实际 40 页）、include `nav.php` **42**、调用 `get_current_company_id()` **66**、写了「超管 + company_id」guard **53**。
- **结论：不成立**。require 库文件只加载函数定义；`company_config.php` 的 HTML 全在 `render_header()` 函数体内，只有调用它的 40 个业务页才输出。且 9 个 API/cron 页（`ai_agent_cron_api.php`、`api_billing.php`、`api_revenue_scrape.php`、`api_stats.php`、`cron_douyin.php`、`cron_tiktok.php`、`cron_youtube.php`、`salary_api.php`、`schedule_api.php`）也 require 了它，顶层 echo 会污染 JSON / CLI 输出。
- **显示层最佳落点是 `render_header()`**（不是文件顶层，也比 nav.php 合适）：它已有 `$is_super = is_super_admin($pdo)` 且输出全站统一顶栏。调用列表含现缺切换器的 `salary_mine.php` / `phone_management.php` / `plan_recharge.php` / `remote_app.php`，可补 4/5；**`hot_news.php` 不调 render_header，需单独处理**。
- **数据层才是难点**：下拉提交 `?company_id=X` 后只有写了 guard 的页面改用 `$selected_company_id` 查询；缺下拉的页面多半也没 guard，加了也不生效。想「一处改动全站生效」只能把选中公司解析下沉到 `config.php:94 get_current_company_id()`（超管时优先 `$_REQUEST['company_id']` / SESSION），66 个调用页自动受益。
- **该下沉的真实风险**：① 函数内若未严格 `is_super_admin()` 校验，普通用户带 `?company_id=2` 即可越权读别家公司；② 写操作（报表/工资/充值）与 `log_operation()`、`log_api_call()` 也用 `$company_id`，超管切公司后保存会落到别家公司名下；③ 该函数有 static 缓存；④ SESSION 记忆会全局污染，退出/切账号需清；⑤ 9 个 API/cron 页输出污染。
- **稳妥折中**：显示层统一到 `render_header()`；数据层新增只供只读列表页显式调用的 `get_effective_company_id($pdo)`（或保留逐页 guard），**写操作继续用 `get_current_company_id()` 不动**。参数统一 `?company_id=`，SESSION 与 `nav_view_company_id` 合并。
