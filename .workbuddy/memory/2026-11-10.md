## [视频嗅探·支持平台页面 URL 下载（YT/TikTok 识别不到）]

用户反馈：`https://www.tiktok.com/@cartooncrack2/video/7704083960841702669` 这样的**页面地址**应能直接下载；且「YouTube 页面识别不到视频」。

### 根因分析
- **主程序下载器 = yt-dlp**，原生支持 TikTok/YouTube/抖音/B站 等大量**页面 URL**（`video_downloader.rs` 有 `extract_video_urls` 白名单：youtube/youtu.be/bilibili/b23/vimeo/tiktok/douyin/kuaishou/xigua/ixigua/weibo/twitter/x/reddit/twitch；服务端 `bwbrowser_resolve.php` 还能解析分享链接）。`enqueue_video_download` 只校验 http(s) → `get_downloader().add_task()` → yt-dlp 自动解析。**所以给页面 URL 即可下**。
- 扩展只把「嗅探到的媒体直链」当可下载对象，而 YT/TikTok 的 `<video>` 是 **blob:/MSE（无 http 直链）**，hook 也抓不到 googlevideo/tiktokcdn → 识别不出 → 不出下载按钮。

### 修复（content.js，仅 JS，需重开浏览器生效）
1. **平台页判定**：新增 `PLATFORM_RE`（复用 Rust 白名单）+ `isPlatformPage()`。
2. **主播放器打分** `scoreVideo`：`duration>0` +3、`!paused&&!ended` +5、`currentTime>0` +2、可见面积加分。平台页里抓出「主播放器」。
3. `collect()`：平台页主播放器若无 http 直链 → `url = location.href`、`viaPage=true`（交 yt-dlp 解析）。
4. `addOverlay` 支持 `viaPage`：按钮文案「下载视频」（区别于普通「下载」），title 注明"解析本页面视频（YT·抖音·TikTok 等平台）"。
5. `engage()` 兜底 `extraPageFallback`：即使 `<video>` 在深层 iframe collect 抓不到主播放器（TikTok 可能），也把 `location.href` 作为可下载项住兜，保证平台页**必然**出现下载入口。
6. 依赖嗅探的补直链/兜底条逻辑全部透传 viaPage，不破坏普通页直链嗅探。

- 已同步 target 部署目录 `target/debug/extensions/video-sniffer/`，`node --check` 三文件语法 OK。
- **生效条件**：需重开爆文库浏览器（content script 改动不热更新）；且之前 verbatim 路径必须已修复（重编译 extension_manager.rs 后干净路径，否则文件缓存不读新内容）。当前 BwBrowser 浏览器未运行，无法实时验证。

## [视频嗅探·按钮滚动后错位（absolute 坐标错配 → fixed）]

用户反馈：页面下滑后按钮不在视频右上角，点「重新识别」希望修正位置。

### 根因
按钮 CSS 是 `position:absolute`（挂 document.body，相对于 body 用文档坐标），但 `placeBtn` 用 `getBoundingClientRect()`（**视口坐标**）定位。两者混用：body 在流内，absolute 相对 body 顶部算偏移，坐标却是视口值 → **页面滚动多少就偏多少**（虽有 scroll 监听重算，但每次算出的仍是「视口坐标 + absolute 相对 body」的错配值）。

### 修复（content.js）
1. 按钮 CSS `position:absolute` → **`position:fixed`**。fixed 相对视口，与 `getBoundingClientRect()` 视口坐标天然匹配 → 滚动时按钮跟随视频移动、永不漂移。

## 暗色问题根因定位 + 修复（2026-11-10 傍晚，重大突破）

### 根因（CDP 实测证据链，profile 6bccb2aa / TikTok explore 页 / 内核 151.0.7922.76）
1. **Wayfern 内核对「未应用过 setFingerprint 的 target」模拟宿主暗色系统表面**（宿主 SystemUsesLightTheme=0 → prefers-color-scheme: dark）。
2. 启动时指纹只发给当时已存在的 target；**启动网址（claude/chatgpt/tiktok 等）是之后才开的标签页** → 从未收到 setFingerprint → 页面恒暗。
3. `browser.theme.color_scheme2=1`（Preferences）、`Wayfern.setFingerprint{prefersDarkMode}`、CDP `Emulation.setEmulatedMedia` 单独用都"无效"的假象：真实原因是内核按 target 在导航时重新施加暗色模拟，刷新后覆盖一切；**只有对这个 target 发过一次 setFingerprint（带不带 prefersDarkMode 都行）后，刷新即恢复浅色**（Preferences cs2=1 修复此时才生效）。
4. 实测对照（reload + iframe 内真实 matchMedia）：仅刷新=dark；发 fp+dark:false 再刷新=light；发普通 fp 再刷新=light。
5. TikTok 页 `data-theme="dark"` 部分是 TikTok 站内主题（账号级），与浏览器无关，但主因是内核暗色模拟。

### 修复代码（需重编译）
- `wayfern_manager.rs`：新增 `reapply_fingerprint_to_page_targets(profile_path, config, kernel_version)` — 取 cdp port → 按 launch 同样方式构建 payload（launch_fingerprint_payload + LOCALE_CARRY_OVER_KEYS 合并 + prefers_dark_mode 注入 + chrome_synced_ua + token）→ get_cdp_targets → 对所有 page target 发 Wayfern.setFingerprint，返回成功数。
- `bwbrowser_cloud.rs` launch_account：`extra_start_urls` 打开循环之后，wayfern profile 且有 wayfern_config 时调用上述方法，日志「指纹已补应用到 N 个标签页（清除内核暗色模拟）」。
- 语法自检通过（rustc 单文件，无解析错误）。

### 排查中的其它结论
- 内核二进制无 `--force-light-mode` 类开关（grep chrome.dll 仅 --default-background-color 等）；headless=new 崩溃不可用于测试；裸 CDP 被"Donut Browser plan"授权拦截（正常实例内 CDP 可用）。
- GUI「颜色方案」Select 的 prefersDarkMode 对内核配色**不生效**（实测），但保留无害。
- 宿主注册表 AppsUseLightTheme=1 / SystemUsesLightTheme=0（应用浅、系统面暗）。

## 用户数据根因确认 + 治本修复（2026-11-10 深夜）
